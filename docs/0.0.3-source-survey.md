# Panopticon Null v0.0.3 — Official Source Survey

**Scope:** Colorado Springs, Colorado procurement surfaces.
**Survey date:** 2026-08-17 (live revalidation).
**Surveyed by:** Panopticon Null build agent, using DNS-safe HTTPS, no cookies, no
credentials, bounded fetches, and the repository's persistent source-review
conventions. All URLs below were fetched with a plain anonymous HTTP client and
their `robots.txt` checked. No authentication, CAPTCHA, or access control was
bypassed. No BidNet or Bonfire account was used and none is required.

This document is the research basis for the v0.0.3 procurement connectors. It is
**not** a claim of comprehensive coverage. Every connector that results from this
survey records its own coverage state in the persistent coverage ledger and never
claims to enumerate a population it cannot verify.

---

## Source authority classification

Panopticon Null assigns every source one of the following authority labels. The
labels are persistent and travel with every observation and citation.

| Label | Meaning |
|-------|---------|
| `authoritative_procurement` | The record is the controlling procurement version (e.g., BidNet / Bonfire). |
| `official_informational_mirror` | City-hosted copy that is informative but explicitly not the controlling version. |
| `official_financial_export` | Official budget/expenditure data export. |
| `official_meeting_or_legislative` | Council or legislative meeting / matter record. |
| `operator_supplied_public_record` | Public record obtained manually or via CORA and imported by an operator. |
| `unreviewed` | Source fetched but not yet reviewed. |
| `restricted_or_inaccessible` | Source that cannot be lawfully automated; represented as inaccessible. |

## Coverage state classification

Every acquisition attempt writes to the persistent coverage ledger a state drawn
from (at least) the following. The default when evidence is absent is `unknown`
or `partial`.

| State | Meaning |
|-------|---------|
| `complete` | Affirmative, reproducible evidence that the checked snapshot enumerates the defined population. |
| `partial` | Evidence covers only part of the defined population. |
| `informational_only` | Source is informative and explicitly not controlling/complete. |
| `access_blocked` | Retrieval was blocked (portal, auth, rate limit, redirect policy). |
| `terms_unreviewed` | Terms/robots not yet reviewed to the project's standard. |
| `schema_changed` | The source's schema/layout changed from a prior snapshot. |
| `unknown` | No affirmative evidence of coverage. |

Absence from a `partial` or `informational_only` source is never proof of
absence. User-facing language states "Not observed in the checked sources" and
never "No contract exists."

## 1. Colorado Springs — Contract Award Information

- **Owning institution:** City of Colorado Springs, Procurement Services.
- **Exact URL:** `https://coloradosprings.gov/procurement-services/page/contract-award-information`
- **Authority class:** `official_informational_mirror`. The page is a City-hosted
  table of awarded contracts. It is informative about awards that have occurred.
- **Completeness statement (source's own):** None found on this page; it does not
  claim to be exhaustive and the sibling solicitation page (see §2) warns that
  City-hosted procurement listings may be incomplete or outdated.
- **Access method:** Plain HTTPS GET. Returns HTML (Drupal).
- **Authentication:** None required.
- **Robots / terms status:** `robots.txt` for `coloradosprings.gov` does not
  disallow `/procurement`, `/solicitations`, or `/budget`. Retrieved with a
  bounded, low-rate, anonymous client. **Approved for lawful automated retrieval**
  under the project's persistent source-review process.
- **Available fields (6-column table, `summary="Table with 6 columns"`):**
  1. RFP/IFB Number (solicitation/award identifier)
  2. Project Name
  3. Awarded Contractor
  4. Awarded Amount
  5. Contract Start Date
  6. Notes
- **Pagination / export:** Single static page. No export offered. 76 data rows at
  survey time.
- **Date coverage:** Contracts with start dates from early 2022 through early 2026
  (survey date). Older rows are retained but the page does not promise a complete
  historical archive.
- **Update frequency (stated):** Not stated on page.
- **Historical records change in place:** Observed formatting irregularities
  (e.g., "Adaman" vs "AdAmAn" Alley, "Asphalitc" vs "Asphaltic", date formats
  `7/1/22`, `1/1/2023`, `April 1, 2024`). The City may edit rows in place;
  therefore a persisted snapshot must be treated as immutable and change detection
  must preserve superseded versions.
- **Known omissions:** The page is not stated to be exhaustive; multiple awards may
  share one RFP number (e.g., `R21-T107KK` Rental Equipment with several
  contractors), and `R22-005NS` Temporary Staffing lists many vendors under
  "various". Not all rows carry a parseable amount.
- **Positive / negative claim support:** Can support a **positive** claim that a
  specific award row was observed in a specific snapshot. It **cannot** support a
  negative claim that no contract exists, because coverage is not proven
  exhaustive.

**Parser notes (formatting irregularities to tolerate without shifting columns):**
- Amount strings: `$42,075.00`, `$0.00 IDIQ` (IDIQ/ceiling), `various`, `N/A`,
  `n/a`, `$300,000 each`, `$0.00`, `$0`, missing.
- Date formats: `7/1/22`, `1/1/2023`, `March 23,2023`, `April 1, 2024`,
  `February 1, 2026`.
- Vendor names containing `&`, `,`, `–`, embedded numbers (e.g., `T010596 Titan`),
  and line-wrap breaks within a cell.
- Duplicate RFP numbers across multiple rows (multiple awardees under one
  solicitation).
- Row-level provenance must be preserved; parsing must never silently shift
  columns.

## 2. Colorado Springs — Solicitation list (City-hosted mirror)

- **Owning institution:** City of Colorado Springs.
- **Exact URL:** `https://coloradosprings.gov/solicitations`
- **Authority class:** `official_informational_mirror`.
- **Completeness statement (source's own, verbatim):**
  > "Solicitations are provided on this page for information purposes only. All
  > RFP's and IFB's... are posted on Rocky Mountain E-Purchasing System. RFP's and
  > IFB's provided on this page may or may not be up to date... The RFP's or IFB's
  > included on Rocky Mountain E-Purchasing System and Bonfire Interactive
  > Procurement Portal remain the authoritative and valid version for procurement
  > purposes. Not all open RFP's and IFB's are listed yet."

  The connector must preserve this warning on every resulting record and must
  **never** claim this page represents every solicitation.
- **Access method:** Plain HTTPS GET. HTML.
- **Authentication:** None.
- **Robots / terms status:** `robots.txt` does not disallow `/solicitations`.
  **Approved for lawful automated retrieval** (informational mirror only).
- **Available fields:** Solicitation title, identifier (e.g., `R26-023AB`), and
  links to City-hosted documents (PDF).
- **Pagination / export:** Static page. City-hosted documents are linked PDFs.
- **Date coverage:** Current open solicitations; not an archive.
- **Historical records change in place:** Yes; open listings are removed or edited.
- **Known omissions:** The page's own warning states it may be incomplete or
  outdated and that BidNet and Bonfire are authoritative.
- **Positive / negative claim support:** **Positive** only, and only for records
  explicitly observed. **Negative claims are unsupported.**

**Related City-hosted documents (R26-023AB transit fare, see §6):**
- `https://coloradosprings.gov/document/r26-023ab-next-generation-transit-fare-collection-system.pdf`
- `https://coloradosprings.gov/document/r26-023ab-submitted-questions-mmt-responses.pdf`
- `https://coloradosprings.gov/document/sample-services-contract.pdf`

## 3. OpenBook COS (financial export surface)

- **Owning institution:** City of Colorado Springs, Finance / Budget.
- **Exact URLs:**
  - Landing: `https://coloradosprings.gov/budget/page/openbook-cos`
  - Launch: `https://coloradosprings.budget.socrata.com/`
  - View-data ("Download or connect directly to this data exported monthly"):
    `https://coloradosprings.budget.socrata.com/#!/view-data`
- **Authority class:** `official_financial_export`.
- **Completeness statement (source's own):** The view-data page states the data is
  "exported monthly." No claim of vendor-level granularity.
- **Access method:** The site is a Socrata single-page application. The data is
  served via the SPA configuration; the underlying SoQL/data REST API is **not**
  reachable through the public standard endpoints
  (`coloradosprings.budget.socrata.com` returns SPA HTML; the four real dataset IDs
  `3mjf-cycw`, `utpe-gz6w`, `9x87-g8nk`, `bxi2-uqix` do not expose a public data
  API from this host).
- **Authentication:** None (public site).
- **Robots / terms status:** `coloradosprings.budget.socrata.com/robots.txt` is
  `User-agent: * / Allow: *`. `coloradosprings.data.socrata.com/robots.txt` is 404
  (not a live data host). The SPA layout is served; the data API is not publicly
  reachable from this host.
- **Available fields (from SPA config, budget-level):** `department_description`,
  `fund_description`, `account_description`, `service`, `budget`. Four datasets:
  revenue, operating budget (Expenses), capital budget, capital projects.
- **Pagination / export:** "Download or connect directly" UI exists, but the public
  data endpoint is not exposed from this host for anonymous automated retrieval.
- **Date coverage:** Budget years as configured in the SPA; monthly export claim.
- **Update frequency (stated):** Monthly export.
- **Historical records change in place:** Budget tables are re-exported monthly;
  prior snapshots may be superseded.
- **Known omissions:** The datasets are **budget-level**, organized by department,
  fund, account, and service. There is **no vendor-level expenditure field and no
  contract/purchase-order identifier** in the exposed schema.
- **Positive / negative claim support:** Can support **neither** a vendor-level
  expenditure positive claim nor a vendor-level negative claim. It supports only
  budget-level observations.

### Negative capability finding (documented, this milestone)

**OpenBook COS cannot connect expenditures to a procurement matter at the vendor
level.** The exposed schema contains department/fund/account/service and budget
amounts but no vendor name, no invoice identifier, and no contract or
purchase-order number. Therefore no vendor-level payment evidence can be sourced
from OpenBook in this milestone. This limitation is proven and visible: the
coverage ledger records OpenBook as `informational_only` (budget-level), and the
expenditure link in the case file is shown as an explicit gap unless evidence from
another lawful source is supplied. **No payment relationship is invented to satisfy
the desired chain.**

## 4. Rocky Mountain E-Purchasing (BidNet) and Bonfire

- **Owning institutions:** BidNet / Rocky Mountain E-Purchasing (third-party
  e-procurement) and Bonfire Interactive (third-party procurement portal).
- **Exact URLs:** Referenced by the City's solicitation page as the authoritative
  procurement versions. Exact portal URLs are behind the City's linked references
  and require portal interaction.
- **Authority class:** `authoritative_procurement` (per the City's own statement
  that BidNet and Bonfire contain the authoritative and valid version).
- **Access method:** Portal-based; registration/authentication, interactive
  searching, and rate controls. **Not suitable for the anonymous, DNS-safe,
  no-credentials HTTP client used by this project.**
- **Robots / terms status:** **Not reviewed to the project's standard.** The
  persistent source-review process has not established that the exact automated
  access method is permitted.
- **Status in v0.0.3:** **Represented as inaccessible** (`restricted_or_inaccessible`
  / `access_blocked` for automation) or **operator-supplied** if an operator
  provides exported public records through the safe import path. **No connector is
  fabricated** and no scraping is performed.
- **Positive / negative claim support:** `none` from automated retrieval in v0.0.3.

## 6. Real case study targets

### 6a. R26-023AB — Next-Generation Transit Fare Collection System (RFI)

Revalidated against the live City solicitation page on 2026-08-17.

- **Identifier:** `R26-023AB` (shown on the City page; a `R26-032AB` variant string
  also appears in an adjacent document link — every identifier must be revalidated
  against the live source and treated as distinct unless an explicit deterministic
  rule links them).
- **Title:** "Next-Generation Transit Fare Collection System RFI."
- **Stage observed:** **RFI** (Request for Information) with a submitted-questions
  / MMT responses document. This is **not** an executed contract and **not** an
  award or purchase. No award or payment record is present on the observed sources.
- **Documents (City-hosted, lawful, public):**
  - `r26-023ab-next-generation-transit-fare-collection-system.pdf`
  - `r26-023ab-submitted-questions-mmt-responses.pdf`
  - `sample-services-contract.pdf` (a sample/example contract, **distinct from an
    executed contract** for this matter).
- **Research rule:** Extract only documented capabilities, data practices,
  requirements, and institutional actions. **Do not label a fare system as mass
  surveillance merely because it handles data.** If no award or payment record is
  available, show that exact gap.

### 6b. Benign control matter

A second, ordinary non-surveillance procurement (e.g., the `Q25-129ZM` NetMotion
Licenses or `Q25-130ZM` LogRhythm Renewal award row, or a routine services award)
is ingested as a **control** to prove that ingestion does not automatically turn
every technology purchase or vendor record into a surveillance accusation.

## 7. Operator-supplied public records (CORA / manual)

- **Authority class:** `operator_supplied_public_record`.
- **Access method:** Safe local import path (CLI `procurement import <path>`).
- **Requirements (enforced):** declared source URL or records-request identifier,
  acquisition date, document role, operator declaration of lawful possession,
  exact file digest, processing provenance, sandbox + resource limits, and human
  review before publication. All supplied files are treated as hostile input.
- **Positive / negative claim support:** Positive only for the specific records
  supplied; coverage stays `partial`/`unknown` for anything not supplied.

## Governing limitations (carried into all connectors and documentation)

- This is **not** comprehensive procurement coverage.
- An **informational mirror is not an authoritative procurement system**; BidNet
  and Bonfire are authoritative and are not automated in v0.0.3.
- **Absence from checked sources is not proof of absence.**
- **Vendor appearance is not proof of procurement wrongdoing.**
- **A technology purchase is not automatically surveillance.**
- **OpenBook may not provide vendor-level payment evidence** (confirmed it does not
  in the exposed schema).
- **Restricted records may require a lawful CORA request.**
- Panopticon Null does not provide legal advice or a legal-compliance guarantee.
